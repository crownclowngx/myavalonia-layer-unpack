# G0015 技术方案：逻辑卷组与按层解压

日期：2026-09-19。状态：**已落实到源码，全部本地门禁通过**。以下职责已通过 ArchiveSource、ArchiveSourceResolver、ArchiveSourceReader、IArchiveExtractor 与 UnpackSession 实现；没有单独引入 VolumePart 或通用调度框架。实际设计与阶段证据见 [核心记录](core-result.md) 和 [界面记录](ui-result.md)。本期范围见 [计划](plan.md)。

## 1. 方案选择

| 选择 | 能解决的问题 | 取舍 |
| --- | --- | --- |
| 仅接入分卷，保留 DFS | 能修复同一父包内分卷无法联合读取 | 改动较小，但多分支仍先深入一个分支 |
| 分卷＋按层串行 | 修复读取，同时符合“这一层结束后再下一层” | 本期推荐；分步验收，较慢的同层任务会推迟所有下一层任务 |
| 引入外部 7-Zip 作为运行时引擎 | 可作为未来独立评估方向 | 增加进程、资产、密码、取消和部署成本，本期不预设引入 |

不是通过“把递归换成队列”就能修复分卷；来源归组与读取适配必须先建立。广度优先描述归档之间的调度，7z 固实包内部仍按引擎要求读取条目，两者不是同一种顺序。

## 2. 最小职责划分

| 建议组成 | 职责 | 不承担的职责 |
| --- | --- | --- |
| ArchiveSource | 不可变逻辑来源、主卷路径、有序卷成员和显示名 | 不打开文件、不持有密码、不调度 |
| ArchiveSourceResolver | 在明确候选集合内按名称和父目录归组、校验编号、去重 | 不解码、不落盘、不扫描任意其他目录 |
| ArchiveSourceReader | 校验所有卷、持有来源句柄与摘要，向引擎提供明确有序来源 | 不决定输出路径或 GUI 行为 |
| IArchiveExtractor / ArchiveExtractor | 完成一个逻辑包的提取及其内容校验 | 不递归、不寻找未经解析的卷、不决定密码轮询 |
| UnpackSession | 密码候选、按深度分桶的当前层和待执行节点、状态、同批次预算、重试及取消 | 不解析卷名、不实现解码 |
| OutputTransaction | 当前逻辑包的暂存、不覆盖提交、回滚和残留报告 | 不负责整个层的整体回滚 |
| Document / View | 逻辑组摘要、诊断、显式恢复入口和关闭生命周期 | 不实现归组、校验或读写规则 |

来源解析可保持一个无状态具体类；只在跨层调用或需要替换读取故障的边界使用窄接口。层序循环留在会话或一个小的内部调度类，不为一个队列引入调度插件体系。所有可变队列、句柄、密码和摘要均属于本次操作／会话。

## 3. SOLID 的落点

- 单一职责：同名归组、读取文件、提取内容、调度后代、提交目录和 UI 分开；修正一种命名规则不必修改解码器。
- 开闭原则：新增标准 7z 分段作为来源形式，复用现有 7z 解码。不同格式以后通过明确适配扩展，不在 UI 叠加多个格式开关。
- 里氏替换：单卷与卷组遵守相同的完整性、取消、资源所有权及不完整不提交契约；替身不得跳过生产端的前置校验。
- 接口隔离：只保留用例和单包读取端口；不用同时包含浏览、压缩、递归、密码和调度的“大归档接口”。
- 依赖倒置：Document 依赖 Headless 用例；会话依赖提取端口。库对象、流及平台句柄不能进入 UI 或 Workflow JSON。

## 4. 读取引擎验证顺序

当前锁定 SharpCompress 0.50.4。该版本 SevenZipArchive 的 SourceStream 路径会加载分段，将其作为逻辑 7z 流读取；这为复用提供依据，不代表已验证整个组合在本插件的异步、取消和预算契约下正确。[锁定版本源码](https://github.com/adamhathcock/sharpcompress/blob/0.50.4/src/SharpCompress/Archives/SevenZip/SevenZipArchive.cs)

G0015-01 首先核实锁定版本可接收显式有序文件流的实际 API，以及 seek、跨边界读取、长度、流释放和同步解码段的取消行为。优先使用库内已有分段设施；不能简单改成“传首卷文件名让引擎自己找卷”，否则会绕过已审核的候选集合与预算。

若已有设施不能满足定位或所有权契约，再评估薄的只读可定位拼接流，限于字节定位和资源管理，不编写 7z 解码。必须补齐边界定位、空读、末尾、取消、超时、异常释放和最大句柄数测试。默认不先复制一个完整 `.7z`，不额外消耗一倍归档大小的磁盘空间。

所有候选均失败时保留负向证据，重新评估独立读取适配或外部引擎的成本；不得通过关闭校验、删除失败样本或将缺卷当正常结束宣称完成。

测试输入使用官方 7-Zip 或可追溯的独立上游样本。现有 G0013 的 7z 创建失败候选不用于证明分卷读取成功。7-Zip 官方说明展示了首段包含开始头、后段包含元数据及结束头的情况，也说明只读首卷不足以还原归档。[7z 结构与分段说明](https://www.7-zip.org/recover.html)

## 5. 契约与调用方兼容

保留 UnpackRequest 接受路径的普通调用方式。GUI 只读预览和 Headless 执行都调用同一个解析器，服务在开始时形成冻结逻辑来源；不能依赖 GUI 先处理一次才能支持分卷。

提取端口从单一路径演进为逻辑来源输入；实施时统一迁移仓库内调用方和故障替身。若保留旧字符串便利入口，必须委托同一解析／校验路径，不能留下两个行为不同的引擎入口。具体新增公开成员须在实现前核对当前 API 使用点。

节点保留 Id、ParentId 和 Depth。SourcePath 继续作为代表路径，完整组使用首卷；缺首卷时保留用户选择路径以便诊断。新增只读成员清单与显示名，用于卷组详情、摘要复验及重新识别。旧单卷结果未提供成员时视为一个来源，不能通过结果重扫磁盘补全。

| 调用方 | 本期兼容要求 |
| --- | --- |
| GUI 添加、扫描、拖放 | 同一解析规则，任意卷归一、重复卷去重；不自动开始 |
| Headless 解压 | 原路径请求有效，解析并冻结逻辑组，原单卷测试保留 |
| 完整检查 | 对整组执行完整内容检查，包含所有卷的预算和源验证；仅目录检查仍保持 ZIP 边界 |
| 普通转换 | 标准 7z 卷组算一个来源，重复卷不生成多个 ZIP；只展开该逻辑包一层，内嵌归档字节保持 |
| 展开整理转换 | 各转换来源的递归会话按层推进，整项共享预算仍累计，不新增跨来源全局调度 |
| 整理／结果打包 | 保持提交清单、源归属和用户筛选语义；不擅自删除原分卷，不用目录重扫代替清单 |
| 无密码 Workflow | 复用 Headless 归组和层序；仍只允许无密码，缺密如实失败；现有动作身份与封闭 Schema 不变 |
| 浏览 | 不因为分卷解压可用就宣称能浏览 7z；只同步能力说明和“全部解压”衔接 |

Workflow 现有结果的 sourcePath 表示代表卷，items 按逻辑包计数。内部多卷元数据不直接塞入现有 v1 JSON；若将来需要公开全部成员，单独设计版本契约。现有输入数量和 JSON 大小限制保持，各卷总数另外受 Headless 上限约束。

## 6. 简洁交互与生命周期

空态保持原添加入口；准备完成显示“项目.7z · 发现 3 个分卷”。默认一条逻辑任务，展开后列出冻结卷路径和发现诊断，实际大小在执行时由读取层校验。执行显示“第 2 层／当前组”，没有可靠总量时不编造百分比；不新增分卷模式、算法、线程或遍历策略选项。

错误分为可确定缺卷、内容／头部损坏歧义、缺密、来源变化、权限及预算。重新识别不自动启动；使用独立临时 Document 任务实例，可复用现有 Document 类型和上下文承载方式，不增加宿主贡献种类。输入字段带入、输出位置可检查，密码不自动带入新会话。

异步选择器返回时核对原 Document 仍可编辑；任务关闭取消并排空所有卷读取、提取及清理。代次检查阻挡迟到回调。成功后打开实际提交目录，不以后来修改的名称重建结果位置。

## 7. 中文注释要求

必须解释：为什么按逻辑包计层、为什么内层仅使用提交清单、为什么连续编号不保证完整、谁持有和释放全部卷流、为什么摘要要覆盖每卷、为什么每层结束后才调度下一层、为什么补齐卷不能使用旧重试快照。同步／异步释放、取消与超时的限制也要写明。

注释采用中文 XML 文档及必要的局部说明。示例不得将测试替身的简化约定冒充生产契约；不承诺全局文件系统原子快照、无限资源或任意时刻都能立即取消。
