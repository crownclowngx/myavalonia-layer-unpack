# G0015：7z 分卷识别与按层串行解压计划

日期：2026-09-19。状态：**01–08 已完成本地开发范围，全部本地门禁通过**。对应 R07 格式读取与诊断的后续增量，调整 G0004 的递归调度；不是 7z 创建功能。用户已授权执行全部计划并分阶段提交 Git，本次实施不运行发布门禁。

## 1. 问题与已确认场景

用户确认：一个外层压缩包完整解开后，在同一文件夹得到 `项目.7z.001`、`项目.7z.002` 等分卷，需要联合读取才能继续解压。不是分别解开多个外层包才能凑齐分卷。

规划基线为 `a1e2a70fdb2e95a98814ada25858697feaa9dfab`。编写时工作区干净；执行本计划前仍需重新核对最新源码、依赖和未提交变更。

规划基线的代码事实（保留问题来源；现行实现见核心记录）：

- [UnpackService](../../../src/LayerUnpackPlugin.Headless/Application/UnpackService.cs) 完整解开并提交一个父包后，发现其输出中的归档，再递归处理子分支，属于串行深度优先。
- [ArchiveProbe](../../../src/LayerUnpackPlugin.Headless/Infrastructure/ArchiveProbe.cs) 可以凭签名识别首卷，但没有分卷归组模型；扩展名表不包含数字卷。
- [ArchiveExtractor](../../../src/LayerUnpackPlugin.Headless/Infrastructure/ArchiveExtractor.cs) 只打开一个来源文件流，禁止引擎自行寻找其他卷；现有能力矩阵明确不支持分卷。
- 因而此次故障主要来自缺少联合读取。当前已经保证单个外层包完整提交后才处理其后代，不能把原因误写成“.002 尚未从同一个父包解出”。

## 2. 目标和边界

目标流程：**本层任务结束 → 从成功提交清单发现下一层 → 按同目录归组分卷 → 串行处理下一层**。GUI 与 Headless 使用同一规则。

本期纳入标准 `名称.7z.001` 起始的数字分段：直接添加任意卷、扫描文件夹、外层解压后自动发现；支持同名组去重、受控联合读取、诊断、密码候选与重试、关闭清理。一个卷组计一个归档节点和一层。默认仍只解一层，用户开启递归后初次为总层数 2，上限 16。

本期不包含 RAR 分卷、ZIP 分卷、通用 `.001` 拼接、分卷创建、7z 创建、非标准名称自动猜测、跨目录收集、下载等待、断点续传或修复损坏内容。`.7z001` 等非标准名称不能直接当作标准规则已支持。保留单卷格式的原有能力与限制。

只调整每个 UnpackSession 内的调度；不引入跨会话全局队列、并行解码、DFS/BFS 设置项、新 Document 或新 Workflow 动作。转换当前按来源独立创建会话，其层序保证在各自会话内，不扩大成整个转换任务的全局层屏障。

## 3. 用户默认路径

1. 添加外层包或任意标准 7z 分卷；直接选卷时就地展示组名和已发现卷数。
2. 检查输出位置；有内层包时开启已有“继续解压内部压缩包”，无需选择分卷模式。
3. 点击开始。先完成本层，再展示下一层逻辑包，分卷只显示一条任务。
4. 成功打开实际输出；部分失败同时保留成功产物和失败原因。缺卷只报告能确定的信息，不把“发现 3 卷”写成“3/3 完整”。

缺卷补齐属于来源变化：首期在失败项提供显式“重新识别此组”入口，带入一个新的解压任务，用户检查后开始；不原地修改旧会话、重做成功外层或自动开始。补密码仍可在卷清单与摘要未变化时重试原节点。详见[卷组契约](split-volume-contract.md)。

## 5. 工程要求

SOLID 为首要约束。来源解析、单包解码、调度、输出事务和呈现分责；接口只设在真实依赖边界，不建立通用策略注册器、插件式调度框架或服务定位器。具体职责与兼容选择见[技术方案](implementation.md)。

新增公开契约、卷边界定位、输入快照、预算计算、层切换、重试和取消代码必须有详细中文注释，解释设计理由、资源所有权和失败后的行为。测试名称、夹具来源及异常案例说明采用中文。注释不重复每行代码，也不能承诺不存在的全局原子快照。

执行本计划时先保护已有工作区变更；保持 Plugin、Document 和 Workflow 的稳定身份。沿用当前精确依赖，不能把上游新版本能力或未通过的 7z 写入候选当作本期读取证据。

## 6. 资源默认值和未确认项

用户尚未提供实际卷组总大小、卷数及最大解出文件大小。**当前默认值先保留**：单输入 4 GiB 改按整组总源字节核算，单个展开文件 2 GiB、批次累计展开 10 GiB。没有用户样本不阻碍普通体量的实现，但不将“大包可用”提前写成承诺。

已新增每组最多 256 卷的有限上限，作为本阶段明确默认策略；目录发现保留现有 100,000 项扫描上界。按整组汇总采用检查溢出的 64 位计算，不按单卷分别获得完整预算；GUI 不展示这些技术参数。

超大样本需求确认后再决定是否调整默认值，并用真实读取、内存、句柄、取消和空间数据验证。Headless 在既有合法范围内提高预算的测试，不等于 GUI 默认支持该体量。读取总量、解码字节、摘要耗时和超时分别记录，避免把合并逻辑误当零成本。
