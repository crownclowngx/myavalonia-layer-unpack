## R04 当前增量：浏览与选择提取

新增 `BrowseDocument / BrowseView` 与稳定 ID `myavalonia.plugin.layer.unpack.document.browse`。单卷 ZIP/ZIP64 可列目录、分页搜索、以条目身份选择文件和目录，一层提取所选并保留相对路径。目录选择是明确后代集合，搜索不改写选择；重复/大小写冲突保留显示，冲突集合不能静默覆盖。

## R02 历史增量：基础 ZIP 压缩

## 1. 已确认需求与本版设计建议

### 1.1 已确认需求

- 作为 MyAvaloniaManagement 的独立插件交付，项目名采用 `myavalonia-layer-unpack`。
- 面向市面上常见压缩包，核心用途是解压。
- 用户可以指定解压深度；深度为 2 时，先解开外层，再解开输出中的下一层压缩包。
- 密码可以跨嵌套层级使用，也可以跨同一批次的多个压缩包使用。
- 拥有自己的 Headless 能力和 Document 页面。
- 不需要 Dock Tool 窗格，不需要历史记忆。

### 1.2 已落地的 V1 设计

以下设计已在本轮实现，参数和行为的最终事实见[执行契约](refactoring/G0002/execution-contract.md)：

- 中文名使用“层解”，Document 显示名使用“解压任务”。
- 一个 Document 管理一个当前批次；可以同时打开多个相互隔离的 Document。
- 使用多个候选密码组成的批次密码池，成功密码在本批次内优先复用。
- 深度默认为 1，允许 1–16；首版不提供“无限”。
- `.tar.gz` 等组合归档按一个逻辑压缩包计一层。
- Headless 首先交付为无 UI 的类库能力；独立 CLI 和跨插件 Workflow 接入作为后续扩展。
- 每个压缩包使用独立输出目录；首版不提供覆盖已有文件和自动删除源压缩包。

## 3. 产品定位与首版边界

### 3.1 一句话定位

> Layer Unpack 是一个批量递归解压工作台：用户一次加入多个压缩包，设置解压深度和候选密码，得到分层清晰、可检查的文件输出与处理结果。

主要场景包括批量资料包整理、多层嵌套包展开，以及一批文件使用相同或不同已知密码的自动尝试。
优先级依次为：解压正确、深度可预测、密码共享明确、结果可解释、取消可靠、格式覆盖。

### 3.2 首版交付范围

| 能力 | 首版目标 |
| --- | --- |
| 文件输入 | 添加或拖入一个、多个压缩包；添加文件夹以发现压缩包 |
| 批量处理 | 多个顶层包形成一个批次，单个包失败后继续处理独立的其他包 |
| 递归解压 | 正整数深度、普通目录不计层、所有分支分别判断是否达到深度 |
| 密码穿透 | 多候选密码、跨层和跨同批次顶层包共享、当前会话内补充密码后重试 |
| 输出 | 同一直接父目录时建议“解压结果”，允许手动调整；独立子目录，展示实际成功位置 |
| Document | 一种临时任务型 Document，输入、设置、进度、结果都在页面内 |
| Headless | 无需创建 Avalonia 窗口或 Document 即可执行同一解压用例 |
| 操作 | 开始、取消、查看失败原因、重试可恢复的失败项、打开输出目录 |
| 状态范围 | 当前批次和 Document 会话，不保存历史记录或跨重启恢复 |

首版不包含压缩打包、压缩包内编辑、密码破解、云端解压、后台常驻队列、暂停后跨重启续传、Dock Tool、
历史任务库、密码管理器或默认全局快捷键。输入已有密码进行有限次尝试，不生成密码字典。

## 4. Document 产品形态

### 4.1 一个 Document 对应一个当前批次

Document 拥有输入清单、输出设置、深度、密码池、当前运行、进度树和结果。
同类型 Document 之间不共享可变任务状态或密码。一个 Document 内同一时刻只执行一个批次。

Document 是工作台的交互载体，不必是可保存文件。首版继续采用普通 Document，不引入 Persistable Document、
任务文件格式、Dirty/保存恢复或撤销历史。解压出来的文件是实际产物，与任务历史是两件事。

### 4.2 页面布局

R01 已采用单列滚动内容和固定底部操作区，Standalone 默认 900×760，最小 640×520。用户无需理解 Headless、引擎或 Scope 即可执行解压。

| 区域 | 默认呈现及按需入口 |
| --- | --- |
| 空状态 | 拖放提示、添加压缩包、扫描文件夹 |
| 处理结果 | 有结果时置于输入之前；摘要、问题列表独立可见，完整树默认折叠，用户选择后展示详情 |
| 输入 | 数量摘要与添加入口；详细清单默认折叠，展开后移除 |
| 输出 | 全部输入直接父目录相同时建议其“解压结果”目录；用户显式选择后不再自动覆盖 |
| 递归 | 默认一层；开启内部解压时初次取总层数 2，才显示层数输入，最大 16 |
| 密码与编码 | 分别通过候选密码和更多选项展开；失败项提供补密或新批次导航 |
| 固定操作区 | 状态、当前项、开始／取消；有已提交产物时“打开结果”为主操作，位置不受下一批参数影响 |

具体状态、焦点和交互验收见[G0007 交互专项](refactoring/G0007/interaction-design.md)。R01 的实现计划和结果独立归档，原 G0001–G0006 执行记录保留为历史。

### 4.3 用户操作闭环

1. 新建“解压任务”，通过空状态添加或拖入文件。
2. 确认输入数量与建议输出；默认解压一层，需要时开启内部解压或展开候选密码。
3. 点击开始，冻结本次执行参数，持续展示当前包和已发现的嵌套关系。
4. 结束后查看完整成功、部分失败或取消结果，并打开成功产物目录。
5. 缺少正确密码时，在当前会话补充密码并显式重试失败节点。
6. 关闭 Document，释放当前任务状态和密码引用；已成功提交的文件仍为用户产物。

运行中不修改正在使用的参数，也不允许重复开始。关闭正在执行的 Document 时，请求取消并等待工作退出，
再释放资源；运行不得静默转交给一个不存在的后台 Tool 或历史队列。

## 5. 解压深度与发现规则

### 5.1 深度定义

- 顶层输入压缩包的层级为 1；解开它需要 `MaxDepth >= 1`。
- 第 N 层解压所得的压缩包层级为 N + 1，普通目录不改变层级。
- 深度限制对每条嵌套分支分别生效，不是整个批次最多执行多少次解压。
- 深度为 0、负数或超过工程上限时，在开始写文件前报参数错误。
- 工程上限由 G0002 的预算设计和 G0004 的验证确定，UI 与 Headless 使用同一验证器。

```text
资料.zip                         第 1 层：MaxDepth = 2 时解开
├─ 说明.txt                       普通文件：正常输出
└─ 附件/                          普通目录：不计层
   ├─ 图片.7z                     第 2 层：解开
   │  └─ 原图.rar                 第 3 层：保留文件，按深度停止
   └─ 表格.zip                    第 2 层：同样解开
```

达到深度是正常停止，不是密码错误或解压失败。对超出深度的文件不启动解压或密码尝试；可以根据可用识别信息
显示“按深度停止”，无法可靠识别时仍作为普通输出文件保留，不为补全树结构越过深度读取内部内容。

### 5.2 文件夹输入与递归发现

文件夹输入扫描子目录，将发现的压缩包列为顶层候选，用户开始前可移除不需要的项。
源目录扫描深度与压缩嵌套深度是两个概念；扫描不跟随目录链接，并排除本批次输出目录。
规范化后相同的输入路径只入队一次，不按文件内容摘要合并不同位置的独立输入。

运行开始后，嵌套发现只针对本次成功解出的文件清单，不重新扫描整个输出根目录，也不接管过去运行的产物。
遇到同层多个嵌套包，分别创建任务节点；排序保持稳定，首版优先使用可预测的串行调度。

### 5.3 组合归档

`.tar.gz`、`.tgz`、`.tar.bz2`、`.tar.xz` 的内容经探测为 TAR 时视为一个逻辑归档，解到 TAR 中的文件占一层。
识别依据由引擎探测确定，不能仅凭重命名的扩展名。普通 `.gz/.bz2/.xz` 解出单一文件同样占一层；
如果该文件是另一个独立压缩包，例如 GZip 中包着 ZIP，继续处理它需要下一层深度。
组合归档内部的流展开仍计入实际资源预算，不因逻辑上只算一层而绕过限制。

## 6. 跨层、跨包密码池

### 6.1 作用域

密码池属于当前批次，服务于该批次所有顶层包和嵌套包。输入 A、B、C 后，可以解开外层用 A、内层用 B、
另一个顶层包用 C 的文件组合，不要求所有压缩包使用同一个密码。

“成功密码复用”仅在本批次的内存中进行，不建立全局密码表，不在 Document 之间共享，也不在下次启动自动恢复。

### 6.2 候选尝试规则

1. 能判断无需密码时直接解压；加密头导致探测也需要密码时，探测与解压共用同一候选策略。
2. 优先尝试本批次已成功使用的候选，再按用户输入顺序尝试其余候选。
3. 对同一节点的同一轮尝试，每个不同候选最多尝试一次；成功后停止后续尝试。
4. 候选耗尽时返回“缺少可用密码”，继续处理其他独立节点，不让整批停在一个密码输入窗口。
5. 用户补充密码后，显式重试相关失败节点；沿用原节点层级和批次深度，不重复展开已成功节点。

UI 可按一行一个候选录入；空行忽略、完全相同项去重，保留密码本身的大小写和首尾空格。
候选数量必须受限。首版不支持含换行符的密码录入，此限制需在输入说明与 Headless 契约中一致表达。

密码错误、压缩包损坏、加密方式不支持、卷缺失应尽可能分别诊断。如果引擎只能给出“密码错误或文件损坏”，
保留这种不确定性，不虚构确定原因。一次密码失败留下的临时输出不得混入下一候选的结果。

### 6.3 无历史记忆的具体含义

- 密码不写入日志、异常文本、结果树、报告、配置、任务快照或遥测。
- 当前会话可保留密码以支持显式重试；清空批次、开始新批次或关闭 Document 时释放密码引用。
- Headless 调用之间不共享候选或成功记录，每次调用由调用方明确提供密码。
- 本地不建立历史数据库、最近任务或自动恢复文件；当前结果树只是运行反馈。

释放引用是生命周期要求，不宣称托管字符串可以被保证物理清零。
未来如果接入会记录参数的 Workflow 平台，需先验证秘密参数传递和脱敏机制，不能直接复用明文密码数组作为可记录输入。

## 7. 格式覆盖策略

“常见格式”不能用扩展名列表代替真实支持证据。下表保留格式家族范围，实际通过的变体、受限和未验证项以[实测矩阵](refactoring/G0003/format-support-matrix.md)为准。

| 格式家族 | 首版目标 | 验证重点 |
| --- | --- | --- |
| ZIP | 普通 ZIP、常见加密 ZIP | Zip64、传统加密、AES、中文文件名、混合加密条目 |
| 7Z | 普通及加密 7Z | 固实压缩、加密头、密码失败与取消 |
| RAR | 常见 RAR4 / RAR5 解压 | 普通与加密样本、固实压缩、引擎发布许可与资产交付 |
| TAR | 普通 TAR | 文件与目录条目、长路径、链接条目的处理 |
| GZip / BZip2 / XZ | 单文件压缩流及常见 TAR 组合 | 组合归档层数、实际字节预算、损坏流 |

首版不将分卷包、损坏修复、自解压 EXE、ISO/CAB 和非常用编码方式列为默认承诺。
缺卷或未支持变体必须给出明确结果，不能静默当作已成功处理。

引擎选择已收敛为 BCL 的 TAR/GZip、SharpCompress 的 7z/RAR/BZip2/XZ、SharpZipLib 的 ZIP，均为托管读取，不启动外部解压进程。ZIP 认证损坏回归促使更换 ZIP 读取器，见[引擎评估](refactoring/G0002/engine-evaluation.md)。

RAR5 加密代表样本的内容已核对，但 MAC 未验证，所有受影响节点附带提示；TAR 要求 UTF-8，旧编码样本明确失败。旧 ZIP 提供 GB18030/UTF-8/CP437/CP866 名称选项，ZipCrypto 密码按 UTF-8。超大 ZIP64、所有 RAR 哈希变体和全部压缩流损坏形式不作通过声明。

## 8. 输出、失败与取消语义

### 8.1 输出组织

用户明确选择输出根目录，每个顶层压缩包得到独立子目录；同名目录已存在时自动增加序号，并在结果中显示实际路径。
嵌套包解到其所在目录中的独立子目录。相同输出根下的并发批次也必须使用排他创建，不能仅靠“先检查是否存在”。

```text
选定输出目录/
├─ 资料/                          资料.zip 的输出
│  ├─ 说明.txt
│  ├─ 附件.7z
│  └─ 附件/                       附件.7z 的输出
│     └─ 图片.png
└─ 图片/                          图片.rar 的输出
```

首版保留源压缩包和输出中的嵌套压缩包，不自动合并、覆盖或删除既有用户文件。
包内重复路径或大小写冲突采用明确报错，避免静默覆盖；输出目录自动编号不代表可任意重命名包内文件。

### 8.2 提交与失败边界

每个压缩包先写入本次拥有的临时目录，验证完成后提交到目标子目录。成功提交后再发现和调度下一层。
提交边界是单个压缩包，不是整批或整棵嵌套树；外层成功后内层失败，外层文件仍可使用。

失败或取消时清理未提交的临时输出，保留已成功提交的产物。清理失败应报告准确残留路径，且不覆盖最初错误。
后续重试只处理选定失败节点及新发现的后代，沿用当前批次记录；不扫描并猜测历史运行状态。

输出路径必须验证在本次目标目录内；绝对路径、父目录逃逸、符号链接或重解析点绕出等情况不得执行写入。
首版拒绝链接类归档条目。累计展开字节、条目数、任务节点数和密码尝试数需要独立于深度的预算，实际写入时持续计量。

### 8.3 状态与进度

| 层次 | 状态 | 说明 |
| --- | --- | --- |
| 批次 | 待开始 / 运行中 / 取消中 / 已完成 / 部分失败 / 失败 / 已取消 | 汇总所有节点；取消后不能显示整批成功 |
| 压缩包节点 | 排队 / 探测 / 解压 / 已解压 / 失败 / 已取消 / 按深度停止 | “已解压”只说明该包本身已提交，后代状态另行汇总 |
| 失败原因 | 缺少可用密码 / 不支持格式或加密 / 文件损坏 / 输入不可用 / 输出错误 / 预算超限 | 结构化原因与面向用户的说明分开 |

部分节点失败且其他节点成功时，批次为“部分失败”；只有按深度正常停止时仍可“已完成”，同时保留停止计数。
批次取消时保留此前成功数与失败数；没有可执行输入时停留在待开始并说明原因。

嵌套包数量通常在处理过程中才知道，界面显示已发现、已完成、失败和当前包进度；没有可靠总量时不编造固定百分比。
Headless 输出相同语义的进度事件。关闭或取消后，迟到的进度与结果不得写回已释放或已开始新批次的 Document。

## 9. Headless、插件与 Host 的职责

### 9.1 目标依赖关系

已建立 `LayerUnpackPlugin.Headless` 类库，承载领域规则、执行用例和解压引擎适配；程序集不引用 Avalonia 或 Plugin SDK。

```text
真实 Host → Plugin Document ───────┐
Standalone → 同一 Document/View ──┼→ Headless 执行用例 → 引擎适配 → 文件系统
无界面测试或未来 CLI ──────────────┘
```

| 部分 | 应当负责 | 边界 |
| --- | --- | --- |
| Headless | 输入验证、深度、密码池、调度、预算、输出提交、取消、结果 | 不依赖 Avalonia、Window、Dock、Document 或 Host 私有实现 |
| Plugin | Module、Document/View、文件选择适配、进度展示和生命周期衔接 | 调用同一 Headless 用例，不在 ViewModel 再写一套解压逻辑 |
| Standalone | 承载真实插件 UI 与 Scope，提供必要开发期端口 | 是 GUI 预览程序，不等于 Headless；不复制业务或 Host |
| Host | 发现插件、创建 Document Scope、Dock 展示和公开生命周期 | 不承担本插件的密码选择和嵌套调度 |

正式插件入口仍只有 `.Plugin`。新增 Headless 及引擎运行时文件需作为插件自有依赖进入干净插件目录，
具体资产声明按[部署与发布说明](deployment-and-release.md)验证；Standalone 和 Tests 不随插件发布。

### 9.2 Headless 用例契约

公开入口为 `IUnpackService.CreateSession(UnpackRequest)`，会话提供 ExecuteAsync、RetryAsync、Snapshot 和可等待释放。实际调用示例见[快速开始](README.md)：

| 方向 | 内容 |
| --- | --- |
| 请求 | 输入路径集合、输出根目录、最大深度、候选密码、旧 ZIP 名称编码、有限资源预算；冲突固定为不覆盖 |
| 运行控制 | 可等待执行、取消令牌、可选进度接收器 |
| 进度 | 本次运行身份、节点与父节点、层级、当前阶段、可靠时的已处理量 |
| 结果 | 批次终态、节点处理结果、成功输出路径、停止原因、错误及清理诊断 |

每次执行使用独立作用域；密码和可变任务状态不能藏在静态变量或插件级单例中。
缺少密码时 Headless 返回结构化失败，不弹窗口或无限等待交互。引擎适配应把不同格式的错误映射到同一结果模型。

### 9.3 后续扩展

CLI、Workflow Provider 与其他插件调用可在本地闭环之后单独立项，复用 Headless。
跨插件调用走公开 SDK 契约，不共享插件私有 CLR 类型或让另一插件直接解析本插件容器。
独立 Headless 能力是首版目标，Workflow 注册不是首版前置条件。

| G0005 Document 完整交互 | 批量添加、参数、密码输入、结果树、取消、会话内补密重试 | 用户可在一个 Document 完成整批解压并定位失败项 | 两个 Document 隔离、绑定与状态、重复开始、迟到回调、Standalone 人工检查 |

## 11. 首版验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| AC01 | 普通 ZIP、深度 1 | 内容与样本一致；内含压缩包保留，未继续解开 |
| AC02 | ZIP → 子目录 → 7Z → RAR、深度 2 | ZIP 与 7Z 解开，RAR 按深度停止；普通目录不占层 |
| AC03 | 外层包含两个内层压缩包、深度 2 | 两条分支均展开，不因已执行两次解压而停止整批 |
| AC04 | 多个顶层包和内层共用一个密码 | 只输入一次候选即可复用；未越过批次作用域 |
| AC05 | 外层 A、内层 B、另一顶层 C | 候选 A/B/C 按策略找到可用密码，各节点正确输出 |
| AC06 | 某包候选耗尽 | 该节点给出密码诊断；独立其他包继续；补密后可显式重试 |
| AC07 | TAR.GZ、深度 1 | 得到 TAR 内容；流展开计入预算，不额外消耗逻辑层级 |
| AC08 | 同名输入与既有输出目录 | 每包输出位置明确，既有文件不被覆盖；同一输入路径不重复执行 |
| AC09 | 内层损坏、格式不支持或输出失败 | 成功产物仍可访问，失败原因明确，批次不误报完整成功 |
| AC10 | 正在写入时取消或关闭 Document | 可观察取消和退出，未提交内容清理，成功内容保留，无迟到状态污染 |
| AC11 | 两个 Document 或两次 Headless 调用 | 参数、任务节点和密码互不泄漏；冲突输出正确隔离 |
| AC12 | 重开 Document 或重启 Host | 不自动恢复输入、密码或历史任务；当前源包及成功产物不受影响 |
| AC13 | 逃逸路径、链接、超预算归档 | 在允许边界内停止，不写到目标之外，不误报成功 |
| AC14 | 无 UI 进程执行同一输入与参数 | 与 Document 调用使用同一用例，输出内容与终态语义一致 |

格式支持以真实样本和引擎版本为证据。原生依赖、取消延迟、内存、磁盘量和大量小文件表现需要记录运行环境与输入规模，
不在验证前承诺固定吞吐或全格式覆盖。通用门禁与证据格式见[质量基线](refactoring/quality-baseline.md)。
