## 2. V1 交付目标与执行约定

### 2.1 用户最终能够完成的操作

- 在 Host 中打开“解压任务”，加入多个压缩包或从文件夹发现压缩包。
- 选择输出位置、解压深度和多个候选密码，启动一次批量解压。
- 密码在同一批次的顶层包和嵌套层级之间复用，深度 2 能解开外层和下一层。
- 查看每个包的进度、输出、失败原因和按深度停止结果；取消运行，或补充密码后重试失败项。
- 关闭 Document 后不保留任务历史或密码；另一个 Document 的任务状态不受影响。
- 在无 UI 环境调用同一套 Headless 能力，得到相同的文件内容与业务终态。

### 2.2 V1 执行边界

| 项目 | 执行约定 |
| --- | --- |
| 身份 | 保留 `myavalonia.plugin.layer.unpack` 与 `myavalonia.plugin.layer.unpack.document.main` |
| 页面 | 一种普通 Document，显示名采用“解压任务”；每个实例只运行一个当前批次 |
| Headless | 新增无 UI 类库，使用同一用例执行解压；不以隐藏 Avalonia 窗口代替 Headless |
| Tool 与历史 | 零 Dock Tool；不建立任务文件、历史库、密码库、Persistable Document 或跨重启续跑 |
| 深度 | 顶层为 1，普通目录不计层，每条分支独立判断；默认按 1 实施，不提供无限深度 |
| 组合归档 | TAR.GZ、TAR.BZ2、TAR.XZ 等按逻辑归档占一层；内部展开仍计入资源预算 |
| 密码 | 当前批次候选池，已成功候选优先；保留大小写及首尾空格，不跨 Document 或调用共享 |
| 调度 | 首版按稳定顺序串行解压；多个 Document 仍可能并行，因此输出占用需防止竞争 |
| 输出 | 每包独立目录，冲突目录自动编号；保留源包和嵌套包，不覆盖既有文件 |
| 提交 | 单包临时写入后提交，外层成功与后代成功分别记录；批次不要求全有或全无 |
| 扩展范围 | CLI、Workflow、分卷、自解压 EXE、压缩打包、损坏修复和后台队列不进入 V1 |

默认深度为 1，上限 16；串行调度和展示名称已落地。参数、预算及验证边界已在 [G0002 契约](refactoring/G0002/execution-contract.md)固定，性能样本见 [G0006 基线](refactoring/G0006/performance-baseline.md)，不以有限规模实测推导所有上限均已满载验证。

### 2.3 格式目标

V1 按产品主文档的格式表实施：ZIP、7Z、RAR4/5、TAR、GZip、BZip2、XZ，以及常见 TAR 组合格式。
ZIP 的常见传统加密与 AES、7Z/RAR 的常见加密和加密头作为样本验证目标。

当前各格式真实样本与支持边界已记录在[格式矩阵](refactoring/G0003/format-support-matrix.md)：ZIP 由 SharpZipLib 1.4.2 解码和校验 AES，其他格式由 SharpCompress 0.50.4 与 .NET 流/TAR 读取器适配。TAR 名称限定可靠 UTF-8；RAR5 加密内容可解，但 MAC 未验证，给出明确警告。分卷与自解压仍不进入 V1。

## 3. 当前基线与目标工程结构

### 3.1 开工基线（历史记录）

以下是 2026-09-07 仅生成计划时的源码事实，保留用于核对前后变化；不代表当前状态：

- 解决方案已有 `LayerUnpackPlugin.Plugin`、`LayerUnpackPlugin.Standalone`、`LayerUnpackPlugin.Tests`。
- `MainDocument/MainView` 仍显示模板内容，Module 注册一条示例 Workbench Command 与 Tools 菜单贡献。
- Standalone 直接构造 Document，并在窗口构造函数中同步等待初始化。
- 没有 Headless 工程、解压引擎、密码池、递归调度或真实解压测试。
- 当前目标为 `net10.0`、Windows x64；公开 SDK 与部署规则按仓库现有配置使用。

### 3.2 目标结构

以下五工程结构现已创建。各阶段档案已补齐，内部类名与最终职责见[工程职责](project-and-window-responsibilities.md)。

```text
src/
├─ LayerUnpackPlugin.Headless/             无 Avalonia / Plugin SDK 依赖
│  ├─ Contracts/                          请求、进度、结果与错误类型
│  ├─ Domain/                             层级、候选策略、状态与预算规则
│  ├─ Application/                        单包/批次执行、递归、重试与取消编排
│  └─ Infrastructure/                     引擎、文件系统与输出提交适配
├─ LayerUnpackPlugin.Plugin/              唯一插件入口，引用 Headless
│  └─ Features/Unpack/                     真实 Document、View 与 UI 适配
└─ LayerUnpackPlugin.Standalone/           承载真实 Plugin UI 和 Scope
tests/
├─ LayerUnpackPlugin.Headless.Tests/       直接引用 Headless 验证无 UI 用例
└─ LayerUnpackPlugin.Tests/                注册、Document、Scope 与交互状态
docs/
├─ product-shape-and-implementation-plan.md
├─ v1-execution-plan.md
└─ refactoring/
   ├─ README.md
   ├─ quality-baseline.md
   └─ Gxxxx/                             各阶段档案已归档
      ├─ plan.md
      ├─ implementation.md
      └─ result.md                       实际结果与待验收项
```

Headless 内部目录体现职责，不要求拆成多个程序集或为每个类建立接口。
无 UI 测试项目不引用 Plugin、Standalone 或 Avalonia，避免无意中依赖已初始化的 UI 环境。
正式插件交付需包含 Headless 和引擎自有运行资产，具体构建声明必须验证，不假定新增 ProjectReference 会自动完成所有打包工作。

## 8. G0004：深度递归与输出闭环

**目标：** 形成可独立使用的完整 Headless 递归能力，包括多分支、组合归档、会话重试与准确结果。

**输入：** G0003 多格式单包执行器与批次密码池。

**工作清单：**

- [x] G0004-01：建立阶段档案与 `recursive-execution-design.md`，固定节点状态、调度顺序、组合归档与重试契约。
- [x] G0004-02：实现层级判断：顶层 1、子包 +1、目录不计层、每分支分别限制；超限节点不进入解压或密码尝试。
- [x] G0004-03：只从本次成功提交的文件清单发现子包，保持稳定次序；不重新扫描整个输出根目录，不重复接管旧产物。
- [x] G0004-04：实现 TAR 组合格式的一层语义，同时验证 GZip 内含 ZIP 需要下一层；组合流展开持续消耗实际预算。
- [x] G0004-05：把同一批次密码池传递给所有允许执行的后代，区分单包已解压、后代未完成和批次最终状态。
- [x] G0004-06：验证嵌套子目录、同名包和并发批次的独立输出；提交后再发现后代，失败回滚仅处理本次未提交内容。
- [x] G0004-07：完善字节、条目、节点和尝试次数预算；批次总预算耗尽后停止后续调度，不因进入下一层、换候选或重试而自动归零。
- [x] G0004-08：实现 Headless 的显式重试用例：针对已记录失败节点、沿用深度及输出归属、只处理失败节点和新后代，不重复成功节点。
- [x] G0004-09：固定重试的源文件变化检测与拒绝规则；区分同一会话内重试和独立新调用，不让无关调用访问已有任务状态。
- [x] G0004-10：验证取消、清理失败和源文件消失，保留成功产物及最初错误；准确汇总部分失败和按深度正常停止。
- [x] G0004-11：完成深度 1/2/3、多分支、跨层 A/B/C、组合归档与递归预算矩阵，校准上限并归档结果。

**状态边界：** 单节点密码错误或损坏允许其他独立节点继续；批次取消、总预算耗尽或无法保证输出边界时停止批次后续调度。
具体错误范围与尚未执行节点的状态必须写入契约，避免所有错误都变成继续或全部中止。
重试只保留当前会话的运行信息和明确提供的候选，不建立持久化任务句柄或密码历史。

**出口验收：** AC01–AC09 在 Headless 中形成完整覆盖，AC10/AC11/AC13 的递归边界通过。
同一个嵌套样本在深度 1、2、3 下得到可核对的不同输出；达到深度仍是正常停止。
外层已成功、内层失败时保留外层产物，重试内层不会再次展开外层。

**交付档案：** 阶段三件套，以及 `G0004/recursive-execution-design.md`；同步 G0002 的用例契约与预算数值。

## 12. 执行命令与证据格式

### 12.1 日常本地门禁

在仓库根目录执行 `./tools/verify-local.ps1`。本轮已通过，实际数量与退出码见 [G0006 结果](refactoring/G0006/result.md)。脚本执行以下检查，并分别输出两个测试项目的 TRX，拒绝零测试、跳过或未通过结果：

```powershell
dotnet restore LayerUnpackPlugin.slnx --locked-mode
dotnet build LayerUnpackPlugin.slnx -c Debug -warnaserror --no-restore
dotnet test LayerUnpackPlugin.slnx -c Debug --no-build
dotnet format LayerUnpackPlugin.slnx --verify-no-changes --no-restore
./tools/check-docs.ps1
```

可用以下命令单独验证 Headless；它不替代整仓回归：

```powershell
dotnet test tests/LayerUnpackPlugin.Headless.Tests/LayerUnpackPlugin.Headless.Tests.csproj -c Debug --no-build
```

Standalone 用 `dotnet run --project src/LayerUnpackPlugin.Standalone` 启动并完成适用交互检查。
当前仅执行 Debug 与原生启停检查。Release、干净部署和正式 ZIP 等到发布时使用[部署与发布说明](deployment-and-release.md)中的构建协议；不要手工压缩 bin 或维护 manifest 副本。
