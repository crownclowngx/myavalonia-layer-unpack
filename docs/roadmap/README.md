# 压缩包工作台：未来产品发展路线图

> 版本：v1.3 · 2026-09-08
>
> 状态：R01、R02 已实施、本地验证通过；R03 已实施、本地 230 项测试通过，见 G0009；R04–R08 规划中。原生人工与发布遗留分别记录。
>
> 用途：先确定每个阶段为什么做、做到什么程度，再为选定阶段生成详细执行计划。
>
> 产品原则：用户带着一个明确任务进入界面，使用合理默认值，快速拿到结果。

## 1. 本路线图与当前版本的关系

当前产品为压缩包工作台 / Archive Workbench，项目为 `myavalonia-layer-unpack`。已有能力包括批量递归解压、当前批次候选密码、补密重试，以及 R02 普通 ZIP 创建、R03 分别打包/规则排除/AES-256；Headless、Plugin 和 Standalone 复用对应业务与界面。

当前事实以[产品主文档](../product-shape-and-implementation-plan.md)、[创建矩阵](../refactoring/G0009/encryption-and-compression-matrix.md)和[G0009 结果](../refactoring/G0009/result.md)为依据。原生交互、DPI、真实 Host 与正式交付仍有待验收项，历史阶段的测试记录不代替新版本证据。

本路线图按实际阶段结果更新。普通 ZIP 创建已在 R02 实现，分别打包和加密已在 R03 实现；浏览、整理与 Workflow 仍为未来功能；路线图本身不触发部署或发布。

编号分工如下：

- `R01–R08` 是产品阶段，编号稳定，用于选择下一阶段。
- `Gxxxx` 是实际实施档案，沿用[文档治理](../refactoring/README.md)的递增规则。
- 一个 R 阶段可以拆成多个 G 阶段；生成执行计划时再根据仓库最新编号分配，不预占或复用 G0001–G0006。
- 每次完成实施后，更新对应 R 阶段的实施映射和状态；只有实际完成的内容才能进入当前能力说明。

## 2. 产品目标与取舍

目标定位为“面向批量资料处理的压缩包工作台”。围绕收到资料、展开查看、提取整理、重新打包交付形成连续能力。

界面主路径始终保持：**放入文件 → 开始处理 → 拿到结果**。选择输出位置和必要的密码属于有实际意义的输入；压缩算法、线程数、底层预算和调度参数不成为普通任务的必答题。

重点用户任务：

| 用户意图 | 产品响应 |
| --- | --- |
| 把这批包解出来 | 默认直接解压；需要时开启内部包递归 |
| 把这些文件发出去 | 默认生成一个 ZIP，名称和位置可检查、可修改 |
| 每份资料分别交付 | 选择分别打包，自动形成明确的一对一输出 |
| 只取包里需要的文件 | 浏览、搜索、选择后提取 |
| 整理复杂资料后重新交付 | 按少量明确规则整理，再生成新包 |
| 重复执行跨插件处理 | 复用 Headless，通过 Workflow 组合 |

本路线图不包含历史任务库、密码持久化、Dock Tool、通用文件管理器、云端解压、压缩包原地编辑、密码破解、自动删除源文件或跨重启续传。CLI / MCP 为候选接入方式，不因存在 Headless 就自动列为交付项。

推荐按表中顺序推进，每完成一个阶段都可以停在有独立用途的版本。依赖列用于说明哪些阶段可在实际需求明确后调整顺序，不代表要求并行开发。

建议交付节奏：

1. R01–R02：先得到简洁、完整的压缩与解压日常工具。
2. R03–R04：补齐批量交付和只取所需的常用场景。
3. R05–R06：形成资料整理与重新打包的特色。
4. R07–R08：根据真实需求扩展格式和自动化协作。

日期与工期在各阶段详细计划中估算；本路线图不把产品阶段直接等同于发布版本。

## 4. 跨阶段共同要求

完整规则见[简洁交互与架构原则](product-principles.md)。各阶段详细计划必须说明：

- 哪些信息默认可见，哪些按需展开，哪些仅由 Headless / Workflow 提供。
- 无需打开高级设置即可完成的代表任务，以及需要用户作出的必要决定。
- 待开始、运行中、完成、部分失败、取消五类状态如何呈现。
- 结果在哪里、源文件是否保留、失败后哪些产物可用。
- 新旧行为如何保持兼容；原有核心能力是否仍可发现和操作。
- 如何证明真实内容正确、取消可靠、会话隔离和状态解释准确。

新增能力不能只以“引擎能够调用”作为阶段完成标准，必须有 Headless 与用户操作闭环。

## 5. 命名与项目身份

R02 已将产品文档与 Standalone 显示名调整为“压缩包工作台 / Archive Workbench”，功能入口仍为“解压任务”“压缩任务”。

仓库名称、程序集和命名空间暂时保留，不把全仓改名放到新增功能的前置条件中。保留 Plugin ID `myavalonia.plugin.layer.unpack` 和现有解压 Document ID `myavalonia.plugin.layer.unpack.document.main`。

新压缩任务、新浏览任务分别分配稳定 Document ID。首次开放后不再因显示名调整而改变身份。同一插件中的两类任务可以同时打开，可变任务与密码仍按 Document / 会话隔离。

## 6. 如何据此生成详细执行计划

使用[阶段执行计划生成模板](stage-execution-plan-template.md)，每次选择一个 R 阶段：

1. 读取当前源码、对应阶段文档、共同原则和最新实施结果。
2. 核对前置能力和未验收项，明确此次真正要实现的范围。
3. 将阶段拆为可验收的工作项，补齐 UI 状态、契约、输出规则和真实样本。
4. 为工作项分配唯一编号，写明依赖、修改位置、完成证据和不做事项。
5. 按现有治理规则建立 G 阶段计划；实施方案和结果在实施过程中据实补齐。

在仅要求生成计划时，不执行计划中的实现或发布动作。详细计划中的待确认技术点应给出推荐选择、验证方式及失败后的收缩方案；日常实现细节由执行者判断，不把所有细节转成用户配置或反复确认。

## 7. 验证与发布边界

文档变更执行 Markdown 路径和状态一致性检查。功能变更遵循[质量基线](../refactoring/quality-baseline.md)，用与变更有关的真实场景和本地检查形成证据。

R01 优先补原生选择、拖放、主题、窄窗口和 DPI 的实际交互证据；缺少环境时准确列为待验收。新增压缩、浏览和 Workflow 后，各自补充对应的真实 Host 检查范围。

正式交付是单独的发布检查：按[部署协议](../deployment-and-release.md)核验资产、干净安装、Host 加载及退出。现有不使用 AIFLOW、不新增 Windows CI、不运行 Release / 正式包 / 部署的本轮边界，不因写入本路线图而改变。后续具体任务明确包含相关操作时，在对应执行计划中列明实际范围。

V1 质量基线中的“一个 Document、零 Workflow”描述的是历史范围。R02 已同步两个普通 Document 的产品契约、注册测试和质量文档；R04 增加浏览入口、R08 增加 Workflow 时继续同步，不修改历史记录来声称过去已经具备这些能力。
