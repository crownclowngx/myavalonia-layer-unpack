# 从产品阶段生成详细执行计划

> 本文件是编写指南和可复制提示词，不是已排期的实施任务。

## 1. 建议使用方式

每次选择一个 R 阶段，结合当前仓库状态生成详细计划。若该阶段包含多个可独立交付单元，可以拆成多个 G 阶段，并逐项写清它们覆盖哪些 R 阶段验收条件。

不要沿用历史测试总数或历史源码摘要作为新阶段证据。生成计划时发现前置条件尚未满足，应列出补齐工作或缩小本次范围，不能以文字将前置阶段改成完成。

## 2. 可复制的任务描述

```text
请根据 docs/roadmap 中的 Rxx 阶段文档，为 myavalonia-layer-unpack
生成该阶段的详细执行计划。本次只生成计划，暂不修改业务源码或执行发布。

先读取：
- docs/roadmap/README.md 与 product-principles.md；
- 所选阶段文档及其前置阶段的实际实施结果；
- docs/product-shape-and-implementation-plan.md；
- docs/refactoring/README.md、quality-baseline.md 和最新 G 阶段记录；
- 与本阶段有关的当前源码、测试、格式矩阵和 SDK 契约。

遵循“默认即可开始、一个页面一个明确任务、复杂选项按需出现”。
对本阶段范围、非目标、依赖、默认行为、UI 状态、Headless 契约、文件输出、
错误恢复、兼容性、真实样本和验收证据作出明确设计。

按照仓库当前编号规则分配新的 G 阶段，不复用旧编号。
将工作项拆到可实现、可验证的粒度，并给出推荐顺序和阶段出口。
对技术不确定点给出验证任务、推荐选择和失败后的收缩方案。
更新路线图中的实施映射，保持“计划完成”和“功能完成”的状态区别。
```

使用时将 `Rxx` 替换成实际编号，并附加本轮已明确的环境、实施范围和限制。

## 3. 详细计划的必需章节

| 章节 | 应写明的内容 |
| --- | --- |
| 基线与问题 | 当前已有能力、缺口、证据位置、对应 R 阶段和前置结果 |
| 目标与非目标 | 用户可以完成的新任务、本次明确不包含的扩展 |
| 用户流程 | 输入、默认值、主要动作、最终产物、代表性失败处理 |
| UI 设计 | 空状态／待开始／运行／完成／部分失败／取消；默认与按需控件 |
| 业务规则 | 命名、目录层级、选择、密码、预算、冲突、源变化和提交边界 |
| 工程方案 | 修改位置、职责、依赖方向、公开契约、生命周期、必要适配 |
| 工作项 | 唯一编号、依赖、交付物、对应验收场景、完成证据 |
| 验证方案 | 真实输入、内容与结构核对、故障样本、UI／Headless／Host 范围 |
| 兼容与迁移 | 稳定身份、现有调用、注册数量、行为变化、文档同步 |
| 不确定项 | 如何验证、默认选择、验证失败后的降级或延期归属 |
| 阶段出口 | 哪些证据齐全才完成；本地、实机和发布状态分别记录 |

## 4. 工作项模板

| 编号 | 工作项 | 前置 | 修改位置或交付物 | 完成条件 | 证据 |
| --- | --- | --- | --- | --- | --- |
| Gxxxx-01 | 用具体行为命名 | 无／明确编号 | 具体契约、页面或文件 | 可观察结果与对应验收编号 | 测试、截图或检查记录 |

工作项应覆盖一个可检查的行为或必要基础。不以“完成所有压缩功能”“优化 UI”这类无法判断边界的标题代替拆解，也不要求按每个方法或属性建立任务。

## 5. 场景模板

每个关键场景写清：前置输入、用户动作、预期文件与目录、预期终态、失败时保留与清理的内容、验证方法。

格式能力必须区分“创建成功”“本工具可读取”“独立读取器或实际目标工具可读取”“内容校验通过”。同一库写入再读回不能单独证明互操作性。

对简洁界面，单独列出一个不展开更多选项的普通任务；对批量功能，列出一个混合成功与失败场景；对落盘操作，列出一个真实写入中取消场景。

## 6. 文档与完成状态

计划生成后记录 G 编号、计划路径和覆盖范围；将对应 R 阶段标为“已生成详细计划”，不能标记已实施。若只覆盖 R 阶段的一部分，明确剩余范围。

实施时按[阶段治理](../refactoring/README.md)维护 `plan.md`、`implementation.md`、`result.md`，必要时补充格式、交互、性能等专项。结果写明实际命令、环境、证据、偏差和遗留，不提前填入通过记录。

源码、依赖或宿主贡献变化时，执行适用的本地检查并同步当前产品文档。纯文档阶段执行 Markdown 路径检查与状态一致性复核。发布检查只在该轮任务明确包含发布范围时执行。
